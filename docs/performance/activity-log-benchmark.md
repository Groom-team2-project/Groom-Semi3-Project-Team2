# 활동 기록 조회 성능 검증

## 검증 배경

활동 기록은 일정·투표·멤버·댓글 변경이 쌓이는 누적 데이터다. 화면에는 최신 20건을 먼저 보이고, 사용자가 `더보기`를 눌렀을 때만 이전 기록을 이어서 조회한다.

여행 계획은 보통 소규모 인원이 함께 관리하므로 수만 건의 로그를 전제하는 것은 서비스 성격과 맞지 않았다. 반대로 몇 건만으로 확인하면 페이지가 깊어졌을 때의 조회 비용을 볼 수 없다. 따라서 수정과 댓글이 비교적 많이 누적된 계획을 가정해 **계획 1건당 300건**을 검증 데이터로 정했다.

처음 검토한 선택지는 `OFFSET` 페이지네이션이었다. 구현은 단순하지만, 새 활동이 계속 앞에 쌓이는 피드에서 페이지 위치가 밀리고 뒤쪽 페이지일수록 건너뛸 행이 많아진다. 무한 스크롤 UX와 맞지 않는다고 판단해 복합 커서 방식으로 구현했다.

## 조회 설계

조회 정렬은 `created_at DESC, log_id DESC`다. 생성 시각만 커서로 사용하면 같은 시각에 작성된 활동의 순서를 고정할 수 없어 누락 또는 중복 가능성이 생긴다. 마지막으로 받은 `created_at`과 `log_id`를 함께 넘겨 다음 범위만 읽도록 했다.

```sql
created_at < :cursorCreatedAt
OR (created_at = :cursorCreatedAt AND log_id < :cursorLogId)
```

이를 지원하기 위해 다음 인덱스를 사용한다.

| 조회 | 인덱스 | 의도 |
| --- | --- | --- |
| 계획별 활동 기록 | `(plan_id, created_at DESC, log_id DESC)` | 계획 조건으로 범위를 좁힌 뒤 안정적인 최신순 커서 탐색 |
| 내 활동 | `(user_id, created_at DESC, log_id DESC)` | 사용자별 활동 기록을 같은 방식으로 탐색 |

한 페이지에는 `size + 1`건을 읽는다. 마지막 한 건은 `hasNext` 판단에만 사용하므로, 별도의 `COUNT(*)` 조회를 추가하지 않는다.

## 테스트 환경

- 로컬 MySQL, 계획 1건, 활동 기록 300건
- 모든 시드 행은 실제 목록 필터에 포함되는 `SCHEDULE_CREATED` 액션
- 로그인한 계획 참여자 1명의 access token으로 API 호출
- 페이지 크기 20건, 정렬은 `created_at DESC, log_id DESC`
- SQL 실행 계획은 동일 데이터에서 확인했고, API 부하는 k6로 실행

300건은 운영 데이터의 최대치를 단정한 수가 아니다. 소규모 여행 계획에서 현실적으로 충분히 누적될 수 있는 양을 택한 것이며, 더 큰 규모를 가정한 결과를 서비스 처리량처럼 제시하지 않기 위한 선택이다.

## 실행 계획 비교

`EXPLAIN ANALYZE`로 같은 20건을 가져오는 과정을 비교했다. 로컬 실행 시간은 캐시 상태에 영향을 크게 받으므로, 여기서는 절대 시간보다 실제로 읽은 행 수를 판단 기준으로 삼았다.

| 조회 방식 | 위치 | 반환 행 | 실행 계획상 탐색 행 | 관찰 |
| --- | --- | ---: | ---: | --- |
| `OFFSET` | 첫 페이지 (`OFFSET 0`) | 20 | 20 | 첫 진입에서는 추가 비용이 없음 |
| `OFFSET` | 중간 (`OFFSET 150`) | 20 | 170 | 앞선 150건을 포함해 읽음 |
| `OFFSET` | 후반 (`OFFSET 250`) | 20 | 270 | 페이지가 깊어질수록 탐색량 증가 |
| 복합 커서 | 150번째 이후 | 20 | 20 | 마지막 커서 이후 범위만 읽음 |

중간 페이지에서 `OFFSET`은 약 0.98ms, 복합 커서는 약 0.06ms로 관찰됐다. 다만 이 수치는 로컬 캐시 영향을 받으므로 성능 개선율로 일반화하지 않았다. 확인한 사실은 페이지 위치에 따라 `OFFSET`의 탐색 행 수가 증가하고, 커서는 필요한 20행으로 유지된다는 점이다.

실행 계획에서는 커서 조회가 `idx_activity_logs_plan_created_log` 범위 스캔을 사용했다. 반면 `OFFSET` 조회는 기존의 `idx_activity_logs_plan_created_at`을 선택했다. 즉, 복합 인덱스가 단순히 추가됐다는 사실보다 **복합 커서 조건에서 실제 선택되는지**까지 확인했다.

## 부하 테스트

SQL만으로는 인증, 계획 참여 권한, 응답 변환 비용을 확인할 수 없다. 그래서 동일 계획의 실제 API에 최신 활동 조회와 151번째 이후 커서 조회를 섞어 호출했다.

| 프로필 | 사용 의도 | 조건 | 결과 |
| --- | --- | --- | --- |
| `journey` | 화면 진입과 일부 사용자의 `더보기` 흐름 확인 | 6 VU, VU당 1회 | 요청 8건, 오류 0건, 체크 24/24 성공 |
| `ramp` | 짧은 시간에 읽기 요청이 몰릴 때 변화 확인 | 3 → 6 → 12 VU, 90초 | 요청 960건, 오류 0건, 체크 2,880/2,880 성공 |
| `steady` | 예상 사용량보다 높은 지속 읽기 여유 확인 | 20 VU, 1분 | 요청 2,320건, 오류 0건, 체크 6,960/6,960 성공 |

| 프로필 | 최신 조회 p95 / p99 | 깊은 커서 조회 p95 / p99 |
| --- | --- | --- |
| `ramp` | 22.89ms / 29.28ms | 19.62ms / 25.95ms |
| `steady` | 50.44ms / - | 34.28ms / - |

`journey`는 요청 수가 8건뿐이라 p95·p99가 통계적으로 의미 없다고 판단했다. 
성공 여부는 위 표에 요청 수·오류율·체크 결과로 남겼다.
반복 요청이 충분한 `ramp`와 `steady`에서는 최신 조회와 깊은 커서 조회 모두 p95 500ms, 오류율 1% 미만이라는 회귀 기준을 통과했다. 이 기준은 운영 SLA가 아니라 같은 로컬 환경에서 기능 변경 후 성능 저하를 감지하기 위한 기준선이다.

## 결과 및 한계

300건에서는 두 방식 모두 사용자에게 느리게 보일 수준은 아니었다. 그럼에도 커서를 선택한 이유는 지금의 병목을 과장하기 위해서가 아니라, 이전 기록을 탐색할 때 읽는 범위가 페이지 위치에 따라 커지지 않게 하기 위해서다. 동시에 같은 시각의 활동도 `log_id`로 순서를 고정할 수 있다.

현재 다른 도메인의 활동 기록 생성 연동이 완료되지 않아, 배포 환경에서는 실제 사용 흐름과 같은 데이터 구성을 재현하지 않았다. 이번 결과는 로컬 조회 성능의 기준선이며, 도메인 연동이 완료되면 별도의 테스트 계획을 준비해 배포된 백엔드 API를 다시 측정한다.
