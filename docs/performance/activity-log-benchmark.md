# 활동 기록 조회 성능 설계

## 1. 문제 정의

활동 기록은 일정 추가·수정·삭제, 투표, 멤버 변경, 댓글 작성 때마다 계속 쌓이는 누적형 데이터다. 사용자는 계획 화면에서 최신 활동을 먼저 보고, 필요할 때만 과거 기록을 이어서 탐색한다.

여행 계획은 보통 3~6명의 소규모 멤버가 일정·투표·댓글을 함께 관리하는 구조다. 활동 기록은 수십 건이 일반적이며, 수정·댓글이 많이 누적된 계획까지 고려해 300건을 상한에 가까운 검증 데이터로 잡았다.

따라서 조회의 핵심은 **첫 페이지가 빠른 것**뿐 아니라, 활동 기록이 충분히 쌓인 계획에서도 **이전 기록을 일정한 비용으로 읽는 것**이다.

## 2. 분석과 설계 판단

### OFFSET을 선택하지 않은 이유

`OFFSET 150 LIMIT 20`은 반환할 20건과 별개로 앞선 150건을 찾아 건너뛰어야 한다. 같은 페이지를 더 뒤로 갈수록 읽어야 하는 행 수도 같이 늘어난다. 무한 스크롤에 부적합한 이유다.

### 복합 커서를 선택한 이유

조회 결과는 `created_at DESC, log_id DESC`로 정렬한다. `created_at`만 커서로 쓰면 같은 시각에 생성된 활동의 순서가 불안정해 누락·중복 위험이 있다. 그래서 다음 두 값을 함께 전달한다.

- `cursorCreatedAt`: 마지막으로 받은 활동의 생성 시각
- `cursorLogId`: 같은 생성 시각 안에서 순서를 결정하는 보조 키

다음 페이지는 마지막 행보다 오래된 범위만 조회한다.

```sql
created_at < :cursorCreatedAt
OR (created_at = :cursorCreatedAt AND log_id < :cursorLogId)
```

이 방식은 페이지 번호가 아니라 마지막으로 확인한 행을 기준으로 하므로, 2번째 페이지와 151번째 이후의 조회 방식이 같다.

### 인덱스 설계

| 조회 화면 | WHERE 조건 | ORDER BY | 적용 인덱스 |
| --- | --- | --- | --- |
| 계획의 최근 활동 | `plan_id` | `created_at DESC, log_id DESC` | `(plan_id, created_at DESC, log_id DESC)` |
| 내 활동 | `user_id` | `created_at DESC, log_id DESC` | `(user_id, created_at DESC, log_id DESC)` |

선행 컬럼은 동등 조건(`plan_id` 또는 `user_id`), 뒤의 컬럼은 정렬·커서 조건 순으로 배치했다. MySQL이 조건에 맞는 인덱스 범위를 최신순으로 읽고 필요한 개수(`size + 1`)만 가져올 수 있게 하는 목적이다.

`size + 1`건을 조회하는 이유는 별도의 `COUNT(*)` 없이 다음 페이지 존재 여부를 판단하기 위해서다. 반환은 `size`건만 하고, 한 건이 더 있으면 `hasNext=true`와 마지막 행의 복합 커서를 내려준다.

## 3. 검증 전략

| 검증 관점 | 확인 방법 | 판단 기준 |
| --- | --- | --- |
| 중간 이후 페이지에서 커서 조회가 OFFSET보다 적은 행을 읽는다 | 300건에서 `EXPLAIN ANALYZE` 비교 | 커서 조회의 실제 읽은 행 수·실행 시간 우세 |
| 실제 API도 이전 기록 조회에서 응답 시간이 급증하지 않는다 | 최신 페이지와 151번째 이후 커서를 동시에 K6 호출 | 각 p95 500ms 미만 |
| 예상 범위를 넘는 동시 조회에서도 실패하지 않는다 | 20 VU, 1분 부하 | HTTP 오류율 1% 미만 |
| 의도한 인덱스를 사용한다 | 실행 계획의 key 확인 | 계획 조회는 `idx_activity_logs_plan_created_log` |

500ms는 로컬 개발 환경의 절대 성능 보장 수치가 아니라, 동일 환경에서 반복 측정할 때 성능 저하를 감지하기 위한 기준선이다. 비교 시에는 DB·서버 상태와 동시 요청 수를 동일하게 유지한다.

### 사용 흐름 가정

- 계획 상세 진입 시 최신 활동을 한 번 조회한다.
- 이전 활동은 사용자가 `더보기`를 눌렀을 때만 커서로 조회한다.
- 활동 기록은 실시간 갱신이나 지속 폴링 대상이 아니다.
- 계획 멤버 수는 소규모이므로, 동일 계획에서 다수 사용자가 계속 이전 기록을 탐색하는 상황은 일반적인 사용 흐름으로 보지 않는다.

따라서 최신 활동 조회와 이전 활동 조회는 목적과 빈도가 다르다. 두 요청을 같은 비중으로 반복하는 것은 실제 행동을 재현하기보다, 읽기 경로의 동시 처리 여유를 확인하기 위한 부하 조건이다.

### 시나리오 구분

| 구분 | 요청 방식 | 의도 | 측정 상태 |
| --- | --- | --- | --- |
| 실사용 흐름 (`journey`) | 6 VU가 최신 활동을 조회하고, 그중 3분의 1만 이전 활동을 추가 조회 | 한 계획의 소규모 멤버가 화면에 진입한 뒤 일부가 `더보기`를 누르는 흐름 확인 | 측정 완료 |
| 피크 여유 (`ramp`) | 3 → 6 → 12 VU로 단계 상승 후 종료 | 일반적인 협업 인원보다 높은 읽기 요청이 짧게 몰릴 때 응답시간 변화 확인 | 측정 완료 |
| 지속 읽기 (`steady`) | 20 VU가 최신·이전 활동 조회를 반복 | 예상 사용량보다 높은 읽기 요청에서도 오류 없이 처리되는지 확인 | 측정 완료 |

`journey`는 실제 화면 사용 흐름을, `ramp`와 `steady`는 읽기 처리 여유를 확인하는 프로필이다. 각 VU에는 `ACCESS_TOKENS`로 준비한 계획 멤버의 토큰을 순환 적용할 수 있다. 토큰 하나만 제공하면 기존 측정처럼 동일 토큰을 공유한다.

아래 측정 결과는 로컬 환경의 세 프로필 실행 결과다. 이를 실제 동시 접속자 수나 운영 환경 처리량으로 일반화하지 않는다.

### 검증 절차

1. 특정 계획에 활동 로그 300건을 1초 간격으로 생성한다.
2. 같은 데이터에서 `OFFSET 150` 조회와 복합 커서 조회의 `EXPLAIN ANALYZE`를 비교한다.
3. `journey`는 최신 페이지를 조회하고, 일부 VU만 151번째 이후의 커서 페이지를 추가 조회한다.
4. `ramp`는 3 → 6 → 12 VU로 단계 상승시키고, `steady`는 20 VU가 1분간 최신·깊은 커서 조회를 반복한다.
5. `journey`에서는 인증·응답 구조·오류 여부를 확인하고, 충분한 반복 요청이 발생하는 `ramp`와 `steady`에서 p95·p99·오류율을 비교한다.

시드 데이터는 모두 실제 피드에 노출되는 `SCHEDULE_CREATED` 액션으로 넣는다. 그러므로 API의 `action_type IN (...)` 필터까지 포함한 현실적인 조회 조건을 검증한다.

## 4. 검증 결과

로컬 환경에서 계획 1건에 활동 기록 300건을 생성한 뒤 세 프로필을 측정했다. 현재 벤치마크 계획에는 참여 사용자가 한 명이므로, 모든 측정은 동일한 access token으로 실행했다. 따라서 인증·계획 참여 권한 검증을 포함하지만, 여러 사용자별 권한 분포 차이까지 검증한 결과는 아니다.

| 프로필 | 조건 | 최신 조회 | 깊은 커서 조회 | 전체 요청 | 결과 |
| --- | --- | --- | --- | --- | --- |
| `journey` | 6 VU, 사용자당 1회 요청 | p95 49.35ms | p95 13.53ms | 8건 | 오류 0건, 체크 24/24 성공 |
| `ramp` | 3 → 6 → 12 VU, 90초 | p95 22.89ms / p99 29.28ms | p95 19.62ms / p99 25.95ms | 960건 | 오류 0건, 체크 2,880/2,880 성공 |
| `steady` | 20 VU, 1분 지속 읽기 | p95 50.44ms | p95 34.28ms | 2,320건 | 오류 0건, 체크 6,960/6,960 성공 |

| 실행 계획 | 결과 |
| --- | --- |
| `OFFSET 150` | 170행 탐색, 약 0.28ms |
| 복합 커서 | 20행 탐색, 약 0.08ms |
| 커서 조회 인덱스 | `idx_activity_logs_plan_created_log` 범위 스캔 |

실사용 흐름인 `journey`에서는 6 VU의 화면 진입·추가 탐색 요청이 모두 성공했다. 피크 여유를 확인한 `ramp`에서는 12 VU까지 증가해도 p99가 최신 조회 29.28ms, 깊은 커서 조회 25.95ms로 유지됐다. 실제 계획 규모를 가정한 300건에서는 두 방식 모두 빠르게 동작했지만, 복합 커서는 이전 기록을 조회할 때 필요한 행만 읽었고 `OFFSET`보다 탐색 행 수가 적었다. 즉, 현재 규모에서 즉각적인 병목을 해소했다기보다 이전 기록 탐색 비용이 페이지 위치에 따라 커지지 않도록 설계한 결과다.

이 결과는 로컬 DB·동일 인증 토큰·읽기 요청만을 대상으로 한다. 네트워크 지연, 여러 사용자 권한 검증, 일정·댓글 작성과 동시에 발생하는 DB 쓰기까지 포함한 운영 처리량을 의미하지는 않는다.
